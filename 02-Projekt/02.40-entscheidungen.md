# E-017

## Titel

Spring Boot Actuator ist Standard für Backend-Monitoring

**Status:** Aktiv

**Datum:** 12.06.2026

### Kontext

Mit Einführung von BL-007 Backend Healthchecks wurde das bisherige Monitoring um anwendungsbezogene Healthchecks erweitert.

Reine Container- oder Portprüfungen liefern keine ausreichende Aussage über die tatsächliche Betriebsbereitschaft der Anwendung.

### Entscheidung

Spring-Boot-Backends werden standardmäßig über Spring Boot Actuator überwacht.

Mindestens bereitzustellen sind:

```text
/actuator/health
/actuator/health/readiness
```

### Begründung

Actuator-Healthchecks ermöglichen die Bewertung der tatsächlichen Betriebsbereitschaft der Anwendung.

Insbesondere berücksichtigt der Readiness-Check zusätzlich die Datenbankerreichbarkeit und besitzt damit einen höheren Aussagewert als reine Container- oder Netzwerkprüfungen.

### Auswirkungen

- neue Spring-Boot-Backends müssen Actuator bereitstellen
- Monitoring erfolgt bevorzugt über Health- und Readiness-Endpunkte
- Uptime Kuma nutzt Actuator-Endpunkte als primäre Betriebsprüfung
- Datenbankverfügbarkeit wird Bestandteil des Betriebsmonitorings

# E-018

## Titel

Laufzeitumgebungen werden über Spring Profiles unterschieden

**Status:** Aktiv

**Datum:** 12.06.2026

### Kontext

Mit BL-007 wurde die technische Umgebungserkennung eingeführt.

Für Deployment, Monitoring und Fehleranalyse muss die aktive Zielumgebung eindeutig identifizierbar sein.

### Entscheidung

Die Laufzeitumgebung wird über das Spring-Profil gesteuert.

Grundlage:

```text
SPRING_PROFILES_ACTIVE
```

Zuordnung:

```text
leer   -> LOCAL
dev    -> DEV
prod   -> PROD
```

### Begründung

Die Verwendung von Spring Profiles entspricht dem etablierten Spring-Boot-Standard und ermöglicht eine eindeutige Identifikation der aktiven Umgebung.

Dadurch können Deployments, Monitoring und Fehleranalysen zuverlässiger durchgeführt werden.

### Auswirkungen

- DEV- und PROD-Deployments setzen `SPRING_PROFILES_ACTIVE` explizit
- die aktive Umgebung wird über `/api/system/info` bereitgestellt
- Fehlkonfigurationen können unmittelbar erkannt werden
- zukünftige Frontend-Anzeigen können die Umgebungsinformation nutzen
- Deployment- und Smoke-Tests prüfen die aktive Laufzeitumgebung

# E-021

## Titel

Image-basiertes Deployment für Frontend und Backend

**Status:** Aktiv

**Datum:** 15.06.2026

### Kontext

Im Rahmen von BL-008 Frontend PROD Image Deployment wurde das Frontend-Deployment an den bereits etablierten Backend-Standard angepasst.

Zuvor wurde das Frontend PROD über Bind-Mounts für dist-Verzeichnis und nginx-Konfiguration betrieben, während das Backend bereits image-basiert deployt wurde.

### Entscheidung

Frontend und Backend werden grundsätzlich image-basiert deployt.

Versionierte Docker Images stellen die verbindlichen Deployment-Artefakte dar.

DEV verwendet Snapshot-Versionen:

```text
X.Y.Z-SNAPSHOT
```

PROD verwendet Release-Versionen:

```text
X.Y.Z
```

### Begründung

Image-basierte Deployments ermöglichen:

- reproduzierbare Deployments
- eindeutige Versionszuordnung
- vereinfachte Rollback-Prozesse
- einheitliche Betriebsprozesse
- konsistente DEV-/PROD-Strategien

### Auswirkungen

- Frontend und Backend folgen demselben Deploymentmodell
- Deployment-Artefakte werden als Docker Images archiviert
- Rollbacks erfolgen über frühere Image-Versionen
- Compose-Dateien und Portainer-Stacks referenzieren versionierte Images
- Bind-Mount-basierte Frontend-Deployments werden nicht mehr verwendet

# E-022

## Titel

Compose-Konfigurationen müssen konsistent geführt werden

**Status:** Aktiv

**Datum:** 15.06.2026

### Kontext

Mit der Einführung versionierter Docker Images für Frontend und Backend wurde deutlich, dass die tatsächliche Deployment-Version von mehreren Konfigurationsebenen abhängt.

Abweichungen zwischen Repository, NAS und Portainer können dazu führen, dass trotz korrekt gebauter Images eine falsche Version deployt wird.

### Entscheidung

Die Compose-Konfigurationen in folgenden Bereichen müssen konsistent gepflegt werden:

```text
EMC-INFRA
→ compose/.../docker-compose.yml

NAS
→ /volume1/docker/compose/.../docker-compose.yml

Portainer
→ Stack Definition
```

Insbesondere müssen Image-Versionen in allen drei Bereichen identisch geführt werden.

### Begründung

Nur konsistente Compose-Konfigurationen gewährleisten reproduzierbare Deployments und nachvollziehbare Rollback-Prozesse.

### Auswirkungen

- Versionsänderungen erfordern Anpassungen in allen drei Konfigurationsebenen
- Deployment-Checklisten prüfen die Konsistenz der Compose-Dateien
- Portainer gilt nicht als alleinige Source of Truth
- EMC-INFRA bleibt die dokumentierte technische Referenz
- Redeployments dürfen erst nach erfolgreicher Konsistenzprüfung erfolgen
- Smoke Tests überprüfen die tatsächlich gestartete Version

# E-023

- selektiver Ausbau der Testlandschaft
- Testbarkeit wird bei neuen Funktionen berücksichtigt
- Qualitätssicherung bleibt langfristig wartbar
- Folgeanforderungen werden risikoorientiert statt coverage-orientiert priorisiert

# E-024

## Titel

Schutz des letzten aktiven Administrators

**Status:** Aktiv

**Datum:** 19.06.2026

### Kontext

Im Rahmen von BL-014 Security Hardening wurde festgestellt, dass ein Administrator versehentlich alle administrativen Berechtigungen aus dem System entfernen könnte.

Dadurch könnte die Anwendung in einen Zustand ohne administrativen Benutzer überführt werden.

### Entscheidung

Die Anwendung stellt dauerhaft sicher, dass mindestens ein aktiver Benutzer mit der Rolle ADMIN vorhanden bleibt.

Der letzte aktive Administrator darf weder:

- deaktiviert werden
- noch auf eine niedrigere Rolle herabgestuft werden

### Begründung

Der Verlust aller administrativen Benutzer würde die Verwaltung des Systems erheblich erschweren und könnte manuelle Eingriffe auf Datenbankebene erforderlich machen.

Die Schutzmaßnahme verhindert diesen Zustand mit geringem technischem Aufwand.

### Auswirkungen

- letzter aktiver ADMIN kann nicht deaktiviert werden
- letzter aktiver ADMIN kann nicht herabgestuft werden
- Verstöße werden mit HTTP 409 beantwortet
- Schutzlogik ist durch automatisierte Tests abgesichert

# E-025

## Titel

Defensive Fehlerbehandlung

**Status:** Aktiv

**Datum:** 19.06.2026

### Kontext

Vor BL-014 konnten technische Fehlermeldungen und interne Implementierungsdetails an Clients weitergegeben werden.

Dies erhöht das Risiko unbeabsichtigter Informationsoffenlegung.

### Entscheidung

Unerwartete technische Fehler werden gegenüber Clients ausschließlich mit einer neutralen Fehlermeldung beantwortet.

Technische Details werden ausschließlich im Backend-Log protokolliert.

Fachliche Fehler bleiben davon unberührt und werden weiterhin mit geeigneten HTTP-Statuscodes und fachlichen Fehlermeldungen zurückgegeben.

### Begründung

Die Trennung zwischen technischen Fehlern und fachlichen Fehlern verbessert die Sicherheit der Anwendung, ohne die Benutzerfreundlichkeit einzuschränken.

### Auswirkungen

- technische Fehler liefern neutrale Fehlermeldungen
- interne Implementierungsdetails werden nicht an Clients übertragen
- fachliche Fehler bleiben sichtbar
- HTTP-Statuscodes werden weiterhin fachlich korrekt verwendet
- Backend-Logs bleiben primäre Fehlerquelle für technische Analysen

# E-026

## Titel

Session Timeout und Cookie-Governance

**Status:** Aktiv

**Datum:** 19.06.2026

### Kontext

Im Rahmen von BL-014 wurde die bestehende Session-Verwaltung überprüft.

Die bisherige Konfiguration war nicht explizit dokumentiert und enthielt keine projektspezifischen Governance-Regeln.

### Entscheidung

Die EMC Mitgliederverwaltung verwendet serverseitige Sessions mit einer festen Timeout-Konfiguration von 30 Minuten.

Zusätzlich gelten folgende Cookie-Regeln:

```text
HttpOnly = true
SameSite = Lax
Secure = true (nur PROD)
```

Die Aktivierung des Secure-Flags erfolgt automatisch über das PROD-Profil.

### Begründung

Die Konfiguration bietet einen angemessenen Sicherheitsstandard für die aktuelle Betriebsumgebung und bleibt gleichzeitig einfach wartbar.

Die automatische Profilsteuerung verhindert manuelle Anpassungen bei Deployments.

### Auswirkungen

- Session Timeout beträgt 30 Minuten
- abgelaufene Sessions erfordern eine erneute Anmeldung
- Session-Cookies sind nicht per JavaScript zugreifbar
- SameSite-Schutz reduziert CSRF-Risiken
- HTTPS-Betrieb in PROD nutzt Secure-Cookies
- DEV und PROD werden automatisch über Spring Profiles unterschieden

# E-027

## Titel

Reporting Startberechtigung

**Status:** Aktiv

**Datum:** 19.06.2026

### Kontext

Im Rahmen von BL-020 Phase 1 Reporting-Grundgerüst wurde die zukünftige Reportingarchitektur definiert.

Dabei wurde festgestellt, dass Reportingfunktionen deutlich höhere Datenschutzanforderungen besitzen als die Anzeige einzelner Mitgliederdaten.

Insbesondere ermöglichen Reportingfunktionen:

* Listenbildung
* Massenauswertungen
* Export personenbezogener Daten
* Erstellung von PDF-, Excel- und CSV-Dateien

Die bestehenden Rollen VIEWER und EDITOR wurden ursprünglich für die operative Mitgliederverwaltung entwickelt und besitzen keine spezifische Reportingdifferenzierung.

### Entscheidung

Für die erste Reportinggeneration werden sämtliche Reportingfunktionen ausschließlich Benutzern mit der Rolle ADMIN bereitgestellt.

Dies umfasst:

* Berichtsauswahl
* Berichtsanzeige
* Filterung
* PDF-Export
* Excel-Export
* CSV-Export

### Begründung

Der konservative Ansatz ermöglicht eine sichere Einführung des Reportings mit geringem technischen und organisatorischen Aufwand.

Datenschutzrisiken durch Listenbildung und Datenexporte werden minimiert.

Eine spätere Differenzierung der Reportingberechtigungen bleibt ausdrücklich möglich.

### Auswirkungen

* Reporting-Menü ist nur für ADMIN sichtbar
* Reporting-Routen sind nur für ADMIN erreichbar
* Reporting-API-Endpunkte sind nur für ADMIN nutzbar
* Exportfunktionen stehen ausschließlich ADMIN zur Verfügung
* bestehende Rollenstruktur bleibt unverändert
* spätere Erweiterung um Reporting-spezifische Berechtigungen bleibt möglich

# E-028

## Titel

Reporting als eigenständiger Fachbereich

**Status:** Aktiv

**Datum:** 19.06.2026

### Kontext

Im Rahmen von BL-020 Phase 1 wurde die zukünftige Integration des Reportings in die EMC Mitgliederverwaltung bewertet.

Zur Diskussion standen:

* Integration des Reportings in den Bereich Mitglieder
* eigenständiger Reporting-Bereich
* hybride Varianten

Zusätzlich wurden Anforderungen an Navigation, Berechtigungen, Architektur und zukünftige Erweiterbarkeit betrachtet.

### Entscheidung

Reporting wird als eigenständiger Fachbereich der Anwendung eingeführt.

Zielstruktur:

```text
Mitglieder

Reporting

Administration
```

Reporting erhält eine eigene Navigation, eigene Frontend-Strukturen, eigene Backend-Komponenten sowie ein eigenständiges Berechtigungskonzept.

### Begründung

Reporting unterscheidet sich fachlich von der operativen Mitgliederverwaltung.

Während die Mitgliederverwaltung der Pflege und Verwaltung von Daten dient, fokussiert sich Reporting auf Auswertung, Analyse und Ausgabe von Informationen.

Die Trennung verbessert Übersichtlichkeit, Wartbarkeit und Erweiterbarkeit der Anwendung.

### Auswirkungen

* Einführung eines eigenständigen Hauptmenüpunktes Reporting
* Aufbau einer separaten Reporting-Architektur in Frontend und Backend
* eigenständige Reporting-API unter `/api/reports`
* Grundlage für zukünftige Berichtsfamilien
* Grundlage für spätere Statistik- und Dashboardfunktionen
* klare Trennung zwischen operativer Datenpflege und Auswertungsfunktionen
